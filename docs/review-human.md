# pyblock.html 審査 — 人間的視点・直感性

実測環境: Playwright / Chromium, 320〜1280px × 文字4段階, localStorage 空から。
Web フォントは実際に読み込んだ状態で撮影。スクリーンショットは `shots/rv-*.png`。
Pyodide は環境都合で動かないので「▶実行」の実行結果そのものは評価対象外。
ただし「実行に何が渡るか」はコード生成関数を直接叩いて確認した。

---

## 1. 総評

100点満点で **42点**。

コードの規律は高い。320〜1280px × 文字4段階の**32通りでページの横はみ出し0件・要素の重なり0件**、
グリップは24px、ARIA も sticky の箱分けも `grid-column` 決め打ちも効いている。ここは疑っていない。

落ちているのは、この企画が自分で「ここで成立が決まる」と書いた2点そのものだ。

- **速さ**: BLOCKS.md は「14タップ＋関数名1回」と書くが、タップの間の**移動量を数えていない**。
  実測で `def tasu(a,b)/return a+b/print(tasu(2,3))` は **16タップ＋レール移動 19,542px（約49フリック）**。
  手打ち56文字より操作数が多い。しかも**レールは1タップごとにスクロール位置が0に戻る**（H-01）。
- **③で Python を見せない**: 写経画面の参照ペインは `def tasu ( a, b ):` `for i in range( 3 ):` を
  そのまま表示している（`shots/rv-12-write-390.png`）。**あれは Python そのものだ。**
  「答えを見る」ボタンが要らないくらい全部出ている。

つまり **土台は丁寧に作られているが、企画の2本の柱が両方折れている**。
配点は 直感性15/40・情報設計8/25・視覚階層10/20・細部9/15 で 42。

## 2. 重大な指摘

### H-01 レールのスクロール位置が、タップのたびに一番上へ戻る

**症状**: `renderRail()` が `rail.innerHTML=''` してから作り直すので、`scrollTop` が 0 にリセットされる。
札を1枚押すたびに、レールが先頭（「ながれ」欄）へ巻き戻る。

**実測**: `scrollTop=2400`（「変数」欄）で `kansu` を押す → 直後 `scrollTop=0`。
レール全長 **3,660px / 表示 594px＝6.2画面分**、75枚。しかも**スクロールバーは
`scrollbar-width:none` で完全に消してある**ので、戻されたことも、下に何枚あるかも分からない。

**誰がいつ困るか**: `i % 2 == 0` を組む人。`i`（offsetTop 2622）→ `%`（1681）→ `2`（1363）→ `==`（1882）→ `0`（1285）と
5枚拾うだけで、毎回0からやり直す。式を1つ作るのにレールを縦に5往復する。

**なぜこうなったか**: 「材料を作って描き直す」設計を素直に書いた結果。
差分更新をしていないので、`ok`（差し先の可否で薄くする）を反映するたび全消しになる。

**どうあるべきか**: 押しても**レールは1ミリも動かない**のが正しい。
描き直すにしても scrollTop を保存・復元する、あるいは `.off` クラスの付け替えだけにする。
これは見た目の話ではなく、H-02 の実測値の半分以上の原因になっている。

### H-02 「10タップ」は成立していない。実測は タップ＋数十フリック

**症状**: タップ数だけ数えて、札を探す移動量を数えていない。

**実測**（390×844・初回・「いつもの」なし。1フリック=400px 換算）:

| お題 | 生成コード | タップ | レール移動 | 相当フリック |
|---|---|---|---|---|
| 1から5までの数を出す | `for i in range(5): print(i+1)` | 8 | **5,902px** | 約15回 |
| 偶数だけ出す | `for … if i % 2 == 0: print(i)` | 13 | **11,141px** | 約28回 |
| 関数を作って呼ぶ | `def tasu(a,b) / return a+b / print(tasu(2,3))` | 16 | **19,542px** | 約49回 |

関数の課題は **16タップ＋49フリック＋キーボード1回 ＝ 実操作約66回**。手打ちは56文字。
**ブロックの方が操作が多い。** 企画書が「ここだけで成立が決まる」と書いた数字が、逆に出ている。

**誰がいつ困るか**: 最初の1本を組む全員。2本目で「打った方が速い」と気づいて戻ってこない。

**どうあるべきか**: 移動量を「タップ数」と同じ一級の指標として測り直すこと。
下の H-10（記号を1列1個で並べている）と H-01 を直せば、机上では 3,660px → 1,200px 程度まで落ちる。

参考: **「いつもの」欄は効いている**。同じお題Aを、6枚が「いつもの」に入った状態で再演すると
移動 **5,902px → 237px**。機構は正しい。問題は**3回押さないと出てこない**こと——
つまり**「この人が続けるかどうかが決まる最初の1セッション」だけ、この救済が効かない**。

### H-03 写経画面が Python をそのまま見せている（企画の中核に違反）

**症状**: `shots/rv-12-write-390.png`。「この形を Python で書く」の下に出るのは

```
def tasu ( a, b ):
  return a + b
for i in range( 3 ):
  if i % 2 == 0 :
    print ( tasu ( i , 1 ) )
```

キーワード・コロン・括弧・演算子が全部そのまま。チップの角丸が付いているだけ。
**学習者がやるのは書き写しになる。** BLOCKS.md が「これをやったら終わり」と名指しした状態そのもの。

**実測**: 「?」で出る模範解答 `def tasu(a, b)\n    return a + b\n…` と、参照ペインの文字列は
**空白の見た目以外まったく同じ**。

**誰がいつ困るか**: 「構造は分かった、記法を思い出す」という②→③の橋を渡る瞬間。
思い出す作業が発生せず、成功体験2（書けた）が偽物になる。

**なぜこうなったか**: 面の行の描画関数 `drawArr` / `paintParts` を写経画面でも**そのまま再利用**しているから。
`paintParts` は `kw(r,'for')` `tx(r,'in range(')` と、Python のトークンを直接書いている。
レールの札は「for 回数」「ぬける」「＝ 入れる」と日本語なのに、**面に落ちた瞬間に英語の Python に化ける**。
抽象化はレールにしか存在しない。

**どうあるべきか**: 面の表現を「Python の字面」から引き剥がすか、少なくとも
**写経画面だけは別の描き方にする**。`for [i] を [5] 回` のように、レールで覚えた日本語のまま出す。
どちらにせよ、いまの形は「答えを見る」ボタンを押す前から答えが出ている。

### H-04 未完成の式をそのまま実行し、生の SyntaxError を出す

**症状**: 実行前ガード `firstHole()` は「式スロットが**空っぽか**」しか見ていない。
トークンが1個でも入っていれば通る。

**実測**:
- `print(i +)` — `firstHole` が `null` を返す＝**ガードを素通りして Python へ渡る**。
- `else:` を1行目に置いただけの状態も素通り（`code()` は `else:\n    print(1)`）。
- `(` だけ入れて `)` を入れない式も同様。

**誰がいつ困るか**: 演算子まで入れて、最後の数を入れ忘れた人。
つまり**H-01/H-02 のせいでレールを探して疲れて、最後の1枚を拾いに行く前に「▶実行」を押した人**。

**なぜこうなったか**: ガードが「穴（hole）」というデータ構造上の空を見ているだけで、
**式が式として成立しているか**を見ていない。

**どうあるべきか**: このアプリの存在理由は「エラーが出たら原因は記法だけだと断言できること」。
**構造が壊れた状態を実行させてはいけない。** 末尾が演算子、括弧の不一致、`else`/`elif` が
対応する `if` の直後にない — この3つだけでも止めれば、生の SyntaxError はほぼ消える。
止めるときは、いまのように「空のところがあります」とトーストを出すだけでなく、
**その行まで面をスクロールさせる**こと（いまは画面外なら何も起きない）。

### H-05 「入力」「数で入力」の札があるのに、標準入力を渡す場所がどこにも無い

**症状**: `runProg()` は `PyRun.run(src, '')`。stdin は常に空文字。
画面のどこにも入力欄は無い（`#scr-build` 内の textarea/input は0件）。

**実測**: `入力` を置いて実行 → `kansu = input()` → 必ず
`EOFError: EOF when reading a line — 入力データが足りません`。100%失敗する。

**誰がいつ困るか**: 「だす・いれる」欄は札が**4枚しかない**。
`print` `print 続き` `入力` `数で入力`。半分が罠。初心者が触らないわけがない。
そして返ってくるのは、このアプリが一番出したくない「原因の分からないエラー」。

**なぜこうなったか**: pydrill の `PyRun.panel` は `showStdin` を持っているのに、
pyblock は `PyRun.run` を直叩きしていて入力欄を作らなかった。実装の取りこぼし。

**どうあるべきか**: 入力ブロックが1つでも面にあるなら、実行の前に**入力を書く場所を出す**。
それが無理なら**その2枚をレールから外す**。動かない札を置いておく方が害が大きい。

### H-06 取り消しが無い。リロードで全部消える。子ごと消える

**症状**: `undo` は存在しない。`PROG` は localStorage に保存されない。`beforeunload` ガードも無い。

**実測**:
- `def tasu(a,b)/return a+b` を組んでリロード → **空**。保存されている項目は `fs` `ord` `hid` `shut` `use` のみ。
- `for`（中に print×2 と if/break）のグリップを面の外へドラッグして離す →
  **4ブロックが一瞬で消える**。出るのは 1.7秒のトースト「消しました」だけ。
- ドラッグ中、消える対象は親の行だけが `.ghosted`（opacity .35）になり、
  **一緒に消える3つの子行は通常の明るさのまま**（`shots/rv-09-kill-390.png`）。
  1行消すつもりで5行消える。

**誰がいつ困るか**: 誤操作をした全員。とくに片手持ちで面の縁を触る人。
そして**ブラウザを間違って再読み込みした全員**。「サンドボックス／気が済んだら残す」を謳う道具で、
30分の作業がタブの再読み込み1回で消える。

**どうあるべきか**: 順に、(1) `beforeunload` ガード、(2) `PROG` の自動保存（保存機能の実装を待たずに）、
(3) 直近1手の取り消し。(3) が無理でも (1)(2) は今日の仕事量。
消すときは**子の数を数えて言う**（「for とその中の3行を消しました」）。

### H-07 親指の届く範囲に、構造をいじる操作が1つも無い

**症状**: 390×844 の画面下1/3（y>563）に入っているのは
**「▶実行」「✎自分で打つ」と、たまたまそこに来ていたレール札5枚だけ**。

**実測**:

| 操作 | 中心 y |
|---|---|
| ⇄ 利き手 / 設定 / レール畳み / ⌫ 全消し | **28** |
| ↑ ↓ ⇥ ⇤ 🗑（移動・字下げ・削除） | **76** |
| ⇤外（挿入点を親の外へ） | 約120 |
| レール札 75枚 | 104〜698（**親指圏は5枚**） |
| ▶実行 / ✎自分で打つ | 803 |

**誰がいつ困るか**: 電車で片手で触る人。つまり想定利用者そのもの。
作者は左利きなので左手持ち＝**右上隅（設定・レール畳み・⌫全消し）が最遠**になる。
`⇄` で左右を入れ替えても、入れ替わるのは**レールと結果柱だけ**で、
上のバーと道具列は動かない（`shots/rv-14-righty-390.png`）。利き手設定が半分しか効いていない。

**なぜこうなったか**: 「上にバー、下に主ボタン」という web の既定の骨格をそのまま採った。

**どうあるべきか**: 「行を選ぶ→動かす／字下げする」はこのアプリの主要ループで、
1本組む間に何度も使う。**道具列（↑↓⇥⇤🗑）と ⇤外 を画面下へ持ってくる**か、
選択中だけ選んだ行の近くに出す。上のバーには「設定」と「全消し」だけ残す。

### H-08 キーボードだけの操作は、2手目で死ぬ

**症状**: `render()` がフォーカスを持っている要素ごと作り直すので、フォーカスが `<body>` に落ちる。
落ちた後は `#canvas` の keydown ハンドラに届かなくなる。

**実測**:
- レール札 `for 回数` にフォーカス → Enter → ブロックは入るが `document.activeElement` は **空（body）**。
  次の Tab は最初（⇄ ボタン）から。
- 面: ↓↓ で2行目にフォーカス（読み上げは正しく出る）→ **Enter で選択した瞬間 focus が body**
  → 以後 `Ctrl+↑` も `Delete` も届かない。`#canvas-help` が説明している
  「Enter で選択、Ctrl と上下で移動」は**順番に実行できない**。
- Tab の巡回順: 上のバー4個 → 見出し15個 → 札75個 → …。**面に着くまで Tab を約95回**。
  ブロックを1個置くごとに0からやり直すので、5行組むのに Tab 約470回。

**なぜこうなったか**: `toggleSec()` だけはフォーカスを戻している（`back.focus()`）。
1箇所だけ手当てされていて、他3箇所（`addStmt` / `selectRow` / `insertToken`）が抜けている。

**どうあるべきか**: `render()` の前後でフォーカス中の要素を識別子で覚えて戻す。
Tab 順は**面を先に、レールを後に**（編集対象が先）。
WCAG 2.5.7 を3回も根拠に挙げている以上、ここは仕様として通っていないといけない。

## 3. 中くらいの指摘

### H-09 レールが持つ唯一の状態表示に、内部の識別子が出ている／幅が足りず切れる

**実測**: `.railnow` の文言は `for_range の式` `print_end の式` `addassign の式` `input_int の式`。
`for_range` は Python の語ですらない。同じブロックがレールでは「for 回数」と呼ばれている。**15pxしか離れていない場所で名前が2つある。**
さらに `中の 2行目に文` は表示幅45pxに対し必要68pxで**省略記号で切れる**——
`⇤外` ボタンが出るのが「中に居るとき」＝文字列が最も長くなるときと重なっているため、**一番読ませたい時に一番読めない**。

**どうあるべきか**: 表示名は `STMT[].r`（レールの札と同じ日本語）から引く。`⇤外` は別の行か、下部の道具列へ。

### H-10 1〜2文字の記号32枚を「1行1個」で縦に並べているのが、レール3,660pxの主因

**実測**: `計算`9 / `比べる`10 / `区切り`4 / `字`5 / `数`4 = **32枚が1〜2文字の記号**。
それぞれ38px高の独立した行を占め、左に**15pxの空の印の桁**を空けて、48px 右から文字が始まる。
`shots/rv-18-symbols-390.png` は `/ // % ** ( ) == != < > <= >=` が縦一列に並んだ図になっている。
この32枚だけで約1,250px。4列のグリッドにすれば約330px。`変数`8 + `道具`13 も2列で半分になる。
合計 3,660px → 約1,900px。H-01 と合わせれば H-02 の移動量は1/4以下になる。

**なぜこうなったか**: 「macOS のソースリスト＝左揃えの平たい行」を全欄に一律適用したため。
参照元の macOS も、記号のパレット（絵文字ビューア、特殊文字）は**格子**で出す。踏襲の範囲を間違えている。

### H-11 入れ子の段差が8px、段差の棒のコントラストが 1.49〜1.93:1

**実測**: 深さ0 のキーワード x=179 → 深さ1 x=187 → 深さ2 x=195 → 深さ3 x=203。**1段8px**。
本文の等幅は12.8pxなので、**1段の字下げが約1文字分**。
段差を担う `.band` は幅3px・`--pencil` に opacity .42/.28/.18 で、面 hsl(276,22%,7%) に対して
**1.93:1 / 1.49:1 / 1.26:1**。WCAG 1.4.11 の 3:1 を全段で下回り、3段目はほぼ地と同じ。

BLOCKS.md は「段差は字下げではなく左の色帯で示す」と書いているが、
その色帯が見えない上に、**分類の色帯（4px, 彩度あり）とすぐ隣で並ぶ**ので区別も付かない。
このアプリが売っている唯一の商品は「構造が見えること」で、その構造が一番見えていない。

### H-12 横スクロールすると、グリップ・分類の色帯・字下げの棒・キーワードが全部流れて消える

**実測**: 390px で3段の入れ子を作ると面は `clientWidth 240 / scrollWidth 345`。
右へ105pxスクロールした時点で、グリップ（x=36）と分類帯（x=65）は**面の左端 129 の外**。
画面には `in range( 5 ):` / `% 2 == 0 :` / `( kansu1 + kansu2 * 3 )` だけが残る
（`shots/rv-04-hscroll-390.png`）。どの行がどれか分からず、掴む所も無い。

`.row{width:max-content}` で行ごと動くのが原因。**グリップ＋色帯＋字下げは左に固定**して、
式の部分だけ流すべき。320px 特大では `+152px` はみ出すので、これは例外ではなく常態。

### H-13 式の途中を直せない。末尾から順に消すしかない

**実測**: `kansu + 1 * 2` の各トークンのうち、押せるのは **`1` だけ**（数・文字列だけ `.tok.edit`）。
`kansu` `+` `*` は押しても何も起きない。唯一の削除手段「1つ消す」は**末尾を1個 pop するだけ**。
先頭の変数を間違えたら、4個消して4個入れ直す。

いちばん頻繁な間違い（変数違い・演算子違い）の復旧費用が、式全体の作り直しになっている。
**どのトークンも押せて、押したら「ここに入れる／ここを消す」が選べる**のが最低線。

### H-14 行を1回タップすると、見えない状態が2つ動く。選択の塗りは 1.34:1

**実測**: `for` の行をタップ → `SEL` が立つのと同時に、**挿入点が for の body の中へ移動する**
（`CARET.arr !== PROG`）。移動先の挿入点は、タップした行から**99px下**に描かれる3pxの線。
選択の塗り `.row.sel` は分類色の16%で、面に対し **1.34:1**。ほぼ見えない。
はっきり変わるのは、画面上端（y=76）の道具ボタン5個が薄灰から明るくなることだけ——
**指から600px以上離れた場所**。

「選ぶ」と「次にどこへ入るか」は別の概念なのに1タップで両方動く。最低でも選択は 3:1 以上で塗ること。

### H-15 ドラッグ中はずっと「はなすと消えます」が出ていて、しかも実行ボタンを覆う

**実測**: `killzone` は `beginDrag` で on、`dragEnd` まで消えない。
**面の上に正しく置こうとしている最中**（緑の挿入線が出ている状態）でも、
画面下に赤い「はなすと消えます」が出続ける（`shots/rv-08-drag-390.png`）。
その札の矩形は y=775〜810 で、**「▶実行」ボタン（y=775〜831）の上に重なり、「実行」の字を隠す**。

加えて:
- ゴーストは `translate(-50%,-50%)` なので、**左へ運ぶと画面外に切れる**。
  実測で `for i in range(5):` が「r i in range(5):」になった（`shots/rv-09-kill-390.png`）。
  左利き＝左へ運ぶ人が最初にこれを見る。
- 削除域は「面と たな 以外の全部」。**レールの上も削除域**。
  「間違えたから元の場所（レール）へ戻そう」という一番自然な動きが、削除になる。

**どうあるべきか**: 赤い警告は**本当に外に居るときだけ**出す。置ける所に居る間は緑だけ。
削除域は下部の明示された帯に限る。ゴーストは指の右上に出して画面内に収める。

### H-16 「たな」に預ける方法がドラッグ1通りしかない（自分で挙げた WCAG 2.5.7 に反している）

**実測**: `SHELF.push` はソース中**1箇所**、`dragEnd` の中だけ。
道具列の5ボタンに「たな」は無い（`ひとつ上へ移す/下へ/内側へ/外へ/消す`）。キーボード経路も無い。

BLOCKS.md と CLAUDE.md は 2.5.7（ドラッグ操作に単一ポインタの代替が必須）を**3回**根拠に挙げている。
レールの札と並び替えには代替を用意したのに、**たなだけ抜けている**。

さらに `たな` は**空でも56px×364pxを常時占有**する。320×568 では画面の10%。
戻す動作（札をタップ）は成立しているので、預ける側だけが欠けている。

### H-17 「?」を1タップすると、確認なしで答えのコード全文が出る。しかも見出しは「結果」

**実測**: 写経画面の右上「?」（40px・無ラベル・aria-label は「答えのコードを見る」）を押すと、
`#w-pre` に `def tasu(a, b)\n    return a + b\n…` が入り、その上の見出しは **「結果」** のまま。

右上の `?` は世間では「ヘルプ」。押した瞬間に演習が終わる操作を、
**戻る／閉じるが置かれる位置に、確認なしで、間違った見出しの下に**置いている。
（もっとも H-03 の通り、答えは既に参照ペインに全部出ている。）

### H-18 分類が「やりたいこと」と「文法」の混在になっている

15欄のうち前半5つ（ながれ／だす・いれる／いれもの／かんすう／じゆう）は「やりたいこと」寄り。
後半8つ（数／計算／比べる／区切り／変数／字／道具／消す）は**文法・品詞の分類**。
CLAUDE.md の約束3「辞書はやりたいことから引く」が、レールでは半分しか守られていない。

具体的な破綻:
- **「区切り」に `[ ] , :` が入っている**。角括弧は区切りではない。
- **`input` が2箇所にある**。「だす・いれる」の文カード「入力」と、「道具」のトークン `input`。別物。
- 「道具」＝ `len range int str float sum max min sorted abs input enumerate zip` の**英語13語がそのまま**。
  レールの他の札が日本語なのでここだけ異物。
- 「字」＝ `'' ' ' '-' 'OK' '\n'`。`'\n'` が生のまま。初学者にこの5枚は読めない。

### H-19 「消す」が5種類、「入れる」が5種類、同時に画面に出ている

画面上の日本語を全部拾って突き合わせた結果:

- **消す**: レール欄「消す」／その札「1つ消す」（式の末尾を1個）／🗑「選んだブロックを消す」／
  ⌫「組んだものを全部消す」／ドラッグ中「はなすと消えます」。**対象が全部違う5つが同居**。
- **入れる**: 「＝ 入れる」（代入）／欄「いれもの」／⇥「ひとつ内側へ入れる」（字下げ）／
  キーパッドの「入れる」（確定）／ヒント「ここに入ります」（挿入）。
- **差し先**: 読み上げは「式の差し先にしました」、トーストは「入れる場所をタップしてください」、
  `.railnow` は「print の式」。**同じ概念に3つの呼び名**。「差し先」は画面に一度も文字で出ない。

### H-20 320px × 特大 で、面が143px。1行も読めない

**実測**: 320px のとき `--rail-w` は文字と一緒に伸びる（小101 / 中108 / 大122 / **特大135px**）。
面はその分だけ痩せる（小177 / 中170 / 大157 / **特大143px**）。
特大で3段の入れ子を作ると横に **+152px** はみ出す。画面に出るのは
`for i in` / `if i %` / `print (` の3つだけ（`shots/rv-07-w320-xl.png`）。

**文字を大きくするほど、プログラムが読めなくなる。** 特大を選ぶのは文字が読みにくい人なので、
救済のつもりの機能が、その人にだけ最悪の結果を返している。
レール幅は `rem` をやめるか、特大では上限を付けるべき。

### H-21 1024px 以上は、電話のレイアウトを横に引き伸ばしただけ

**実測**（1024×1024, `shots/rv-07-w1024-m.png`）:
- 「▶ 実行」が **幅846px**。56px高の紫の帯が画面を横断する。
- 道具ボタン5個が**各約190px**。中に13pxの矢印が1つ。全部 disabled のときは、
  幅192pxの灰色のスラブが5枚並ぶだけになる。
- 「たな」が **幅962px×56px** で、中身は左端の12pxの案内文のみ。
- 面は600px、結果柱は850pxが空白。

`flex:1` に上限が無いのが原因。iPad 横／PC は「使える幅が増えた」のに、
増えた幅が**ボタンの横幅**にしか使われていない。

### H-22 名前入力と全消しが OS のダイアログ（`prompt` / `confirm`）

`def` の名前 → `prompt('関数の名前','tasu')`、`じゆう` の行 → `prompt('この行に書く Python')`、
⌫ → `confirm('組んだものを全部消しますか？')`。

BLOCKS.md は「関数名だけはキーボードを許す、それ自体が学習内容」と書いている。
その**学習内容が、アプリの外観をぶち破る灰色のシステムダイアログで出る**。
iOS Safari では画面上部に URL 付きで出る。設定シートもキーパッドも自前で作ってあるのに、
一番大事な「名前を付ける」瞬間だけ既製品になっている。

### H-23 設定シートが画面の86%を覆い、レールを見ないまま並べ替えることになる

**実測**: シートは y=118〜844（726px / 画面の86%）。15行を52pxで並べ、**同時に見えるのは8行**。
`.sbody` の中身は1,202pxで、シート自体もスクロールする（入れ子スクロール）。
並べ替えても**トーストは出ず**、読み上げだけ（「ながれ を 1番目にしました」）。
結果は**閉じるまで見えない**。

さらに:
- **「色の見分け」を名乗っているのに、15個のチップのうち8個が同じ紫**（数/計算/比べる/区切り/変数/字/道具）。
  「じぶん」と「かんすう」も同じ桃、「いつもの」と「じゆう」と「消す」も同じ灰。
  凡例として見ると「この8つは同じ物です」と言っている。
- 名前が3通り: ボタンの aria-label「文字の大きさとレールの並び」／
  シートの題「レールの設定」／中の見出し「レールの並び ／ 色の見分け」。
  そして**先頭にあるのは「文字の大きさ」でレールの設定ではない**。
- 「ぜんぶ たたむ／ひらく」が「レールの並び ／ 色の見分け」の下にある。並びでも色でもない。

### H-24 キーパッドの「やめる」が「0」の隣。パッドが面の下157pxを隠す

**実測**: パッドは y=541〜844（303px・画面の36%）。面の下端は698なので、**面の下157pxが隠れる**。
いま編集している数がそこにあると見えない。背後に暗幕（scrim）は無く、`aria-modal:false` で
背後のレールも押せてしまう。

キーの並びの最下段は `0 | やめる | 入れる(2枠)`。**一番押す「0」の右隣が「やめる」**（85px幅、隣接）。
打ち間違いが「破棄」に直結する。`←`（1文字消す）も「戻る」に読まれやすい。

### H-25 トーストが上のボタンを覆い、指から586px離れた所に出る

**実測**: `.toast{top:14px}`。「ぜんぶ たたみました」（幅156px, x=117〜273）は
**`⇄` と 設定ボタンに重なる**（`shots/rv-06-collapsed-390.png`）。

（`入れる場所をタップしてください` / `消す場所をタップしてください` / `これ以上は動かせません` /

## 4. 細部の妥協

### H-26 「レールを畳む」と「全部消す」が、どちらも“線の入った長方形”で隣り合っている

上バーの3番目が分割矩形アイコン（sidebar toggle）、4番目が `⌫`（U+232B, 中にXの入った角丸長方形）。
40pxで並ぶと**ほぼ同じ形**（`shots/rv-01-first-390.png` 右上）。
片方は無害、片方は**確認1回で全作業が消える**。この2つを隣に置いて似た形にしてはいけない。

### H-27 🗑 だけが絵文字

上バーの4つと道具列4つは線画（SVG または記号文字）。5つ目の `🗑` だけが絵文字。
この検証環境では単色で出たが、iOS / Android では**カラー絵文字**になり、`color:var(--bad)` は効かない。
8個のアイコンの中で1個だけ質感が違う物が、しかも**削除ボタン**にあたる。

### H-28 「なにもしない」だけ2行に折り返して、レールのリズムが崩れる

**実測**: レール札の行高は 40px か 38px（記号）で揃っているが、`なにもしない` だけ **68px**。
108px幅に6文字が入らない。「ながれ」欄の末尾で、そこだけ列が間延びする。

### H-29 見出し 8.32px / 個数バッジ 8px・3.56:1

- 欄の見出し（ながれ／だす・いれる…）は **8.32px**。日本語を大文字化＋字間.16em で組んでいる。
- 個数バッジ（9, 4, 3…）は **8px かつ opacity .55 → コントラスト 3.56:1**（AA 未満）。
- `.railnow` は 8.64px、`⇤外` ボタンの字は 8.96px、「たな」ラベル・「結果」ラベルは 8.8px。

**8〜9pxの文字が5通りの大きさ（8 / 8.32 / 8.64 / 8.8 / 8.96px）で9箇所に散っている**。文字サイズを4段階用意しても、`rem` 基準なので特大でも 10.4px。
「拡大しなくて済むようにする」という設計意図と、実際の字の大きさが噛み合っていない。

### H-30 空の面が最初に教えるのが「消える」こと。しかも改行が壊れている

**実測**（390px）: ヒントは4行に割れて
`レールのブロックをタップする` / `と ここに入ります` / `つかんで動かす / 外へ出すと` / `消える`。
**「タップする」と「と」の間**で切れている。中央揃え・幅制限なしで手書き体のため。
320×568 では **7行・176px＝面の高さの55%** を食う。

内容も、まだ1つも作っていない人に向かって
**2文のうち1文が削除の話**。最初に伝えるべきは「レールの札を押すと1行できる」だけでいい。

### H-31 「結果」欄が、答えを出すときも「結果」のまま

H-17 と同じ場所。`#w-out` を「実行結果」と「模範解答」の2用途で使い回していて、
ラベル `.lab` を書き換えていない。`showAnswer()` は `pre.className='idle'`（灰色）にするだけ。

### H-32 「この形を Python で書く」が PYTHON と表示される

`.ref .lab` に `text-transform:uppercase`。DOM は `Python` だが画面は `PYTHON`。
同じ規則で「たな」「結果」も大文字化の対象になっている（日本語なので影響が出ないだけ）。

### H-33 ⌫（全部消す）が、広い画面の結果柱を消さない

**実測**（1024px）: `clearAll()` は `document.getElementById('out')`（電話用）だけ `hidden=true` にする。
`out-desk`（980px以上で使う右の柱）はそのまま。
全部消した後も右柱に前回の出力 `1` が残り、`LAST.code` も `print(1)` のまま残る。

### H-34 関数に名前を付けた瞬間、レール全体が下へずれる

「じぶん」欄は中身が0件なら描かれない（`if(!sc.rows.length)return`）。
名前を確定した瞬間に**レールの先頭に欄が1つ生まれ、以下の全部が約75px下へ動く**。
名前を付けた直後は引数を入れに行く場面なので、指の行き先が変わる。

### H-35 数の常備が `0 1 2 10`。3・4・5 が無い

BLOCKS.md の旧案は `0 1 2 3 5 10 100`。実装は4枚。
`range(3)` も `tasu(2,3)` も、`3` を出すのに「数を書く」→キーパッド→「入れる」の3手が要る。
一番よく使う小さい数が抜けている。

## 5. AI っぽく見える箇所

すべて「どの要素が、なぜ」で挙げる。

1. **道具列（`.tools`）の5つ**。同じ幅・同じ角丸13px・同じ影・同じ間隔6pxで横一列。
   1024pxでは各192pxまで均等に伸びる。**5つが等価だと言っているが、
   🗑 だけが不可逆**。重みの差が形に一切出ていない。テンプレの「ツールバー」そのもの。

2. **影が全部同じ**。`--raise-sm`（-3px -3px 7px / 3px 3px 7px）が、
   上バーのアイコン・道具ボタン・たなの札・設定シートの行のボタン・キーパッドのキー・
   `⇤外`・`とじる`・`はじめの並びに戻す` に**同じ値で**付いている。
   1つの影の定義を全要素に配って回った結果、材質の差が消えて全部が同じ高さの板に見える。

3. **角丸が4段（22/16/13/7）用意されているのに、実際は13と16にほぼ集約**。
   `.ic` 13 / `.tools button` 13 / `.rail` 16 / `.canvas` 16 / `.out` 16 / `.shelf` 16 /
   `.seg button` 13 / `.orow` 13 / `.pad .keys button` 13。四隅も全部同じ半径。
   「トークンを作ったので使った」だけで、大きさと役割の対応が無い。

4. **ヒント文の中央揃え**（`.hint{text-align:center}`）。
   面は左揃えのコード領域で、その中の唯一のテキストだけが中央に来る。
   壊れた改行（H-30）はこれが原因。

5. **15欄が完全に同じ形**。見出し30px＋札39px の反復が3,660px続く。
   「ながれ9枚」と「消す1枚」と「道具13枚」が同じ組版で並ぶ。
   内容の性質が違う（文カード／記号／英語の関数名）のに版面が1種類しかない。

6. **手書き体で書かれた開発者の理屈**。設定シートの
   「読みにくいときは拡大せずここで変える。／ 画面ごと拡大すると横にはみ出して戻せなくなる。」
   これは実装メモであって、学習者に向けた言葉ではない。
   Yomogi で書けば人間味が出るというのは、まさに手癖。

7. **上中央の pill 型トースト**（`border-radius:999px`, `top:14px`, 1.7秒）。
   Material / Bootstrap の既定の見た目そのままで、しかも上バーのボタンを覆う（H-25）。

## 6. 良い所

世辞抜きで、設計判断として効いている物だけ。

- **「いつもの」欄**。実測でレール移動 5,902px → **237px**。効き方が桁違い。
  集計を「読み込み時と設定を閉じた時だけ」凍らせる判断も正しい——指の下で並びが動かない。
- **ドラッグ判定を「レールの外へ出たか」にしたこと**。縦120px動かしてもドラッグにならず、
  横へ抜けた瞬間に始まることを実測で確認した。縦スクロールと両立している。
- **`.rsec` で sticky の含みブロックを節ごとに切ったこと**。見出しが積み上がらず常に1枚。
  スクロールさせても崩れなかった。
- **`grid-column` を決め打ちしたこと**。`--pane-w:0` の幅で面が潰れる事故が実際に起きない。
  32通りの検証で**レイアウトの破綻は0件**。これは珍しい。
- **分類色の明度選定**。実測でレール札 8.34:1、見出し 8.81:1。
  文字として使う分には全色 AA を余裕で超えている（破綻しているのは H-11 の3px帯と H-14 の塗りだけ）。
- **数をブロックに直接書き込むキーパッド**。`1` の札を探させない、という判断そのものは正しい。
  小数も負数も入る。（並びの問題は H-24。）
- **`user-scalable=no` を使わなかったこと**。`touch-action:manipulation` ＋ 入力欄16px固定 ＋
  画面内の文字サイズ、という3点の分解は正確。（実装の帰結が H-20 なのは別の話。）
