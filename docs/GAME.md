# GAME.md — キャラを Python で動かす（要件定義と作業プロセス）

2026-09-19 起案。`docs/BLOCKS.md` の続き。**この文書の数字はすべて実測**で、推測は「未測」と書く。

---

## 0. 何を作るのか

**すでに居るキャラを Python で動かす。動かす仕組みを、そのまま別のゲームに応用できる形で持つ。**

出発点は依頼主の原体験そのもの——Scratch でキャラを動かし、弾幕を作り、
**その「動かす仕組み」を応用してマリオのような別ジャンルへ持っていこうとした**。
面白かったのは絵が出たことではなく、**仕組みが手のうちにあって、他へ効いたこと**。

だから本企画の成否は「絵が描けるか」ではなく、
**一度作った動きが、次のゲームに持ち越せるか**で決まる。

## 1. 前提の訂正（先に潰した誤解）

- **pygame は Pyodide 0.28.3 に入っていない。** 343パッケージを全数確認した。
  `pillow` `numpy` `matplotlib` `imageio` `scikit-image` はある。`pygame` / `pygame-ce` は無い。
  （pygame-ce の wasm 版は pygbag という別のツールチェーンで、Pyodide とは同居しない。）
- よって **「pygame を動かす」ではなく「pygame 風を自作する」**。
- ただし**名前と形は pygame に寄せる**。あとで本物の pygame に移るとき、
  `Sprite` `Group` `rect` `blit` という語彙が そのまま効くようにする。
  逆に `pygame.init()` `display.flip()` のような定型は隠す——
  定型文こそ「文字を書くのに10分かかってエラー」の正体だから。

## 2. 技術の地面（実測 2026-09-19）

### 2-1. フレームの予算

Worker の Python が `update()` を回し、状態だけを main に返して main が描く方式。
Chromium / 1フレームの予算 16.67ms に対して:

| スプライト | fps | Python | Worker往復 | 描画 | 予算の消費 |
|---|---|---|---|---|---|
| 200 | 60.2 | 0.36ms | 0.60ms | 0.21ms | 4% |
| 500 | 60.1 | 0.65ms | 0.90ms | 0.45ms | 7% |
| 1000 | 60.1 | 1.20ms | 1.48ms | 0.87ms | 12% |
| **2000** | **60.2** | 2.16ms | 2.40ms | 1.64ms | **25%** |

**弾幕に必要な数（数百）は余裕で入る。** 2000体でも予算の1/4。
状態は `array.array('f')` を `transfer` で渡す＝コピーしない。

### 2-2. 画像の置き場

IndexedDB に Blob で置き、`createImageBitmap` で復号:

| | 保存 | 読込 | 復号 | 備考 |
|---|---|---|---|---|
| 16×16 PNG（115B） | — | 0.80ms | 1.50ms | |
| 512×512 PNG（8KB） | 0.40ms | 0.40ms | 2.20ms | |

**リロードしても残ることを確認済み。** 起動時に全キャラを復号しても、10体で 20ms 台。

### 2-3. まだ測っていないこと（未測）

- 実機（古い Android / 低電力の iPhone）での fps
- 音（Web Audio）を足したときの負荷
- 100体以上のキャラ画像を IndexedDB に置いたときの起動時間

## 3. 用語

| 語 | 意味 |
|---|---|
| **スプライト** | 読み込んだキャラ1体。画像＋名前。Python では `Sprite` |
| **グループ** | 同じ種類のスプライトの集まり（弾、敵）。Python では `Group` |
| **ステージ** | ゲームが映る場所。canvas 1枚 |
| **毎フレーム** | 1/60秒ごとに1回走る所。ここに動きを書く |
| **仕組み** | 当たり判定・重力・スクロールなど、持ち越せる仕組み |

既存の語（本体／下書き／棚／レール／面）はそのまま使う。
**新しい語を5つ以上 増やさない**（審査 H-19）。すべて一般的な用語を使い、造語をしない。

## 4. アーキテクチャ

### 4-1. 役割の線引き（これが全部を決める）

> **Python は論理を持つ。JS は画素を持つ。橋は「状態の数値」だけ。**

- Python が持つもの: 位置・速度・向き・コマ番号・見える/見えない・当たり判定の箱・ゲームの規則
- JS が持つもの: 画像そのもの（ImageBitmap）・canvas・入力の受け取り・描画
- 橋: 1フレームあたり `Float32Array`（1体につき x, y, 角度, コマ, 見える の5つ）

**Python は画素に一度も触らない。** これで 2000体 60fps が成立している（§2-1）。
Pillow を使って Python 側で画像をいじる設計にしたら、この数字は出ない。

### 4-2. 1フレームの流れ

```
main(rAF) ──入力の状態──▶ worker ──▶ Python update() ──▶ Float32Array
    ▲                                                          │
    └──────────── transfer（コピーなし）───────────────────────┘
    │
    └─▶ ctx.drawImage × N
```

- **ループを回すのは JS**。Python 側に `while True` を書かせない。
  （書かれたら worker が固まって中断も効かない。既存の `walkWhy` ガードで止める）
- 入力は main で拾って worker へ渡す。キーボードと**画面上のパッド**の両方。

### 4-3. 既存の PyRun との関係

`PyRun` は「1回走らせて出力を返す」道具で、ゲームの常時ループとは別物。
**同じ worker を使い回さない。** `GG` という別の worker を立てる。
理由: 実行中の中断・再起動の意味が違うし、`PyRun` の約束（押した瞬間にだけ取りに行く）を壊さない。

## 5. Python 側の API（`gg`）

**定型は隠す。名前は pygame に寄せる。**

```python
import gg

jiki = gg.Sprite('jiki', x=180, y=400)      # スプライト1体
tama = gg.Group('tama')                      # グループ
teki = gg.Group('teki')

@gg.loop                                     # 毎フレーム（ここが 1/60秒ごと）
def _():
    if gg.key('right'): jiki.x += 5
    if gg.key('left'): jiki.x -= 5
    if gg.key('fire'): tama.add(jiki.x, jiki.y, vy=-9)

    tama.move()                              # グループを速度ぶん動かす
    tama.kill_off_screen()                   # 画面の外へ出たら消す

    if teki.hit(jiki):                       # 当たったか
        gg.stop('MISS')
```

### 5-1. 最小の語彙（第1版）

| 種類 | もの | pygame の対応 |
|---|---|---|
| スプライト | `gg.Sprite(名前, x, y)` / `.x .y .angle .frame .visible` | `pygame.sprite.Sprite` / `.rect` |
| グループ | `gg.Group(名前)` / `.add(x,y,vx,vy)` `.move()` `.hit(相手)` `.count` | `pygame.sprite.Group` |
| 入力 | `gg.key('right')` `gg.tap()` | `pygame.key.get_pressed()` |
| ループ | `@gg.loop` | `while running:` + `clock.tick(60)` |
| 場 | `gg.width` `gg.height` `gg.stop(文)` `gg.score` | `display` |

**`gg.loop` は1つだけ。** 2つ書いたらエラーにする（構造が曖昧になる）。

### 5-2. 決定（2026-09-19 確定）

- **識別子は ASCII。** Python 3 は日本語の識別子を許すが採らない。
  生成された Python をそのまま外へ持ち出せることを優先する
  （写経画面・合鍵・本物の pygame への移行）。
  画面のラベルは日本語でよいが、**生成コードは常に ASCII**（`jiki` `tama` `teki`）。
- **座標は y が下向きに増える。** canvas と pygame に合わせる。
  Scratch は上向きなので、そこだけ感覚が変わることは承知のうえ。
  **本物の pygame へ移ったとき座標の読み替えが要らないことを優先する。**
- **UI の語彙は一般的な用語を使う。** ひらがなで平易にしない。
  対象は 18歳で、すでにプログラミングを知っている。
  この方針は 2026-09-19 にアプリ全体へ適用済み
  （制御 / 入出力 / 変数 / 関数 / 自由記述 / 数値 / 演算 / 比較 / 名前 / 文字列 / 組み込み / 削除、
  札は `for range` `break` `pass` のように Python の名前をそのまま出す）。

## 6. ブロックへの写像

**ここが本企画の肝。** 打つのではなく、まず組めなければ意味がない。

### 6-1. engine の変更が要らない部分

- `ねこ.x` は**ただの文字列トークン**。`isName()` は `/^[A-Za-z_][\w.]*$/` で
  **すでにドットを許している**（実測確認済み）。`insertToken('jiki.x')` がそのまま通る。
- `+=` は既存の `addassign` 札がそのまま使える。
- `@gg.loop` は body を持つ文＝`for` や `if` と同じ形。`hasBody` に1語足すだけ。

### 6-2. 新しく要るレールの欄

| 欄 | 中身 | どう埋まるか |
|---|---|---|
| **スプライト** | `jiki` `jiki.x` `jiki.y` `tama` … | **読み込んだキャラから自動で生える**（`じぶん` 欄が `def` から生えるのと同じ仕組み） |
| **うごき** | 毎フレーム / キーが押されている / うつ / 動かす / 画面の外で消す / 当たった？ / やめる | 固定 |

`じぶん` 欄の `userFuncs()` と同じ形でよい＝**既存の仕組みの写し**。
分類の色は **6色目を足さない**。`スプライト` は `box`（いれもの＝青）、`うごき` は `flow`（ながれ＝橙）に寄せる。

### 6-3. ステージ（canvas）をどこに出すか

- **組み立て面の上に重ねない。** 面は面のまま。
- **「あそぶ」を 4枚目のタブにしない**（H-07 で帯が苦しい）。
  **▶実行 を押したら ステージ が結果欄の位置に出る**＝いまの「結果」の場所がそのまま canvas になる。
  文字を出すプログラムなら文字、スプライトが居るプログラムなら ステージ。**同じ場所**。

## 9. リスクと、その潰し方

| # | リスク | 潰し方 |
|---|---|---|
| R-1 | **`while True` を書かれて worker が固まる。** 中断ボタンも効かない | ループは `@gg.loop` 1つだけ。`while True` は実行前ガードで止める（`walkWhy` に1行） |
| R-2 | **スコープが膨らむ。** 「マリオも作れる」＝衝突・重力・タイル・カメラ・音…で別アプリになる | フェーズを切る（§10）。各フェーズの出口条件を先に決め、満たすまで次へ行かない |

| R-4 | 他人の画像を読み込んで配れると 権利が破綻する | 合鍵にはコードだけ入れる。画像は端末内（F-15） |
| R-5 | ブロックで書けない動きが出る | `じゆう` 札で逃がす（既にある）。逃げた先が頻出なら札にする |
| R-6 | ゲームが「お題」化して また学校になる | **お題を作らない。** 見本は「こわして遊ぶ元」として置く |

## 10. 作業プロセス

フェーズごとに**出口条件**を決める。満たすまで次へ行かない。
各フェーズの終わりに `verify.py` が緑であること、360〜1280px で壊れないことを確認する。

### Phase 1 — 動く1体（土台）★ 実装済み 2026-09-19（実機確認 待ち）

入れたもの:

- **`GG` worker**（`PyRun` とは別）。`gg.py` を Pyodide の FS に書いて `import gg`。
  Python へ渡す値は `py.globals.set` に置く——**文字列の中に文字列を作らない**
  （最初 `json.loads('...')` を worker ソースの中で組み立てて壊れた）。
- **`gg` モジュール**（`docs/gg.py` が正本）。`Sprite` / `Group` / `key` / `loop` / `stop` /
  `clamp` / `hit` / `move` / `cull` / `count`。素の CPython で単体検証済み
  （当たり判定 frame 46、clamp が 16/344 で停止、500発が60フレームで全消、
  `@gg.loop` の2つ目は拒否、バッファは可変長）。
- **ステージ**（canvas 360×480）。▶実行 で結果欄と同じ場所に出る。
- **遊びはモード**（`body[data-gg="on"]`）。レール・面・棚・道具列を隠して、
  ステージと操作パッドだけにする。
- **操作パッド**（十字46px＋ボタン72px）＋キーボード（矢印・Space・Z）。
- **レールの ゲーム 欄**（16札）と **スプライト 欄**（プログラムから自動で生える）。

実測: **60〜61fps**。canvas に 434画素が描かれ、→ を押しっぱなしで
x が 331〜356 まで動いて `clamp(16)` で止まることを確認。

生成されるコード（ブロックだけで組んだもの）:

```python
import gg
jiki = gg.Sprite('jiki', 180, 400)
@gg.loop
def _():
    if gg.key('left'):
        jiki.x += -5
    if gg.key('right'):
        jiki.x += 5
    jiki.clamp(16)
```

**engine の変更はほぼ不要だった**（§6-1 の読み通り）:
`jiki.x` はただのトークン、`+=` は既存の `addassign`、
`@gg.loop` は `hasBody` に1語と `gen` に1行。
スプライト欄は `assign` の式が `gg.Sprite` / `gg.Group` で始まる物を拾うだけ。

踏んだ罠:

- **`.pad` がクラス名で衝突していた。** 数値キーパッド（`position:fixed` ＋
  `translateY(110%)` ＋ `visibility:hidden`）を丸ごと継いで、操作パッドが
  画面外に居た。`.gpad` に改名。
- **`flex-basis:auto` の箱に aspect-ratio の canvas を入れると余りを食い尽くす。**
  ステージが 583×777 に膨らんでパッドを箱の外へ押し出した。`flex:1 1 0` にする。

**出口条件のうち未達**: 依頼主の実機での 60fps 確認。

### Phase 1 — 出口条件（原文）

- `GG` worker（PyRun とは別）
- `gg.Sprite` / `gg.key` / `@gg.loop` / `gg.width` `gg.height`
- 内蔵キャラ 3体
- ステージ（結果欄の位置に canvas）
- 画面上のパッド（← → ↑ ↓ ＋ ボタン1つ）
- レールに「スプライト」「うごき」欄

**出口**: 電話で、ブロックだけで組んで、自分の指でキャラが動く。実機で 60fps。

### 見本（2026-09-19 追加・実機で遊べることを確認済み）

| 名前 | 中身 | 実測 |
|---|---|---|
| **たまよけ** | 降ってくる弾をよける。`gg.score` をフレーム数に使い、`% 14` で弾を湧かす | SCORE 73→181、弾が降る、**61fps** |
| **たまを撃つ** | ● で撃つ。`tama.count < 4` で連射を抑える。敵は `teki.vx` を反転して往復 | ● 押しっぱなしで **20点**（2発 命中）、**60fps** |

**`global` を使わずに済ませている。** カウンタは `gg.score`（モジュール属性）、
敵の速度は `teki.vx`（インスタンス属性）。どちらも代入が束縛ではなく属性への代入なので、
`global` 宣言が要らない。**ブロックに `global` 札を足さずに状態を持てる**、というのが理由。
